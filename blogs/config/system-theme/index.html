A dark terminal in a light desktop is a flash of glare every time the window changes focus. This setup makes the terminal own the palette instead of teaching every tool to read the desktop on its own: WezTerm follows the system appearance and hands it on to Claude Code, OpenCode and the Starship prompt inherit its palette, and Neovim checks the OS directly because a full-screen application cannot see the terminal palette.

Install on a new machine
#

Install directly from GitHub:

1curl -fsSL https://raw.githubusercontent.com/tihaya-anon/tihaya-anon.github.io/main/scripts/install-theme-config.sh | sh

The script downloads the repo archive and copies the files to ${XDG_CONFIG_HOME:-$HOME/.config}, moving any different existing file to a timestamped backup first:

1dotfiles/wezterm/wezterm.lua  -> ~/.config/wezterm/wezterm.lua
2dotfiles/wezterm/keys.txt     -> ~/.config/wezterm/keys.txt
3dotfiles/zsh/starship.toml    -> ~/.config/starship.toml
4dotfiles/opencode/cli.json    -> ~/.config/opencode/cli.json

Under WSL the terminal is the Windows build of WezTerm, which never reads the Linux home. Both installers detect WSL, ask cmd.exe for %USERPROFILE%, and write wezterm.lua and keys.txt to %USERPROFILE%\.config\wezterm\ instead.

WezTerm checks ~/.config/wezterm/wezterm.lua before ~/.wezterm.lua. If the latter already exists, the installer writes to that file instead of adding a higher-priority config that would shadow it, and backs it up first.

Check the plan without changing anything:

1curl -fsSL https://raw.githubusercontent.com/tihaya-anon/tihaya-anon.github.io/main/scripts/install-theme-config.sh | sh -s -- --dry-run

Use --no-backup to fail instead of replacing an existing file, or --ref to read the files from another branch. The scripts replace whole files rather than merging local edits, so run --dry-run first and keep the timestamped backups. If the repo is already cloned locally, run the same installer from the checkout:

1sh scripts/install-theme-config.sh

The Zsh installer writes the same theme files and also handles ~/.zshrc, which holds the Claude Code appearance hook, ~/.zprofile, and the plugins. Running either script is enough; run both and the second one reports the shared files as up to date.

The scripts install configuration only; WezTerm, Starship, OpenCode, and a Nerd Font still need to be installed separately.

How the appearance flows
#

This is the current setup:

LayerAppearance sourceHow it switches
WezTermDesktop appearance APIReloads the config when the system changes
StarshipMocha bar, ANSI colors outside itBar stays; prompt symbols follow WezTerm
OpenCodeTerminal palette and appearanceFollows the terminal while the TUI runs
Claude CodeTerminal background, else COLORFGBGChecks when a session starts
NeovimOS settings, not the terminalRefreshes on focus and resume

The terminal is the only place that needs a desktop-specific check. The COLORFGBG fallback reads the result from a file WezTerm leaves behind, OpenCode reads the terminal’s reported appearance, and Starship’s few unfilled colors come straight from the terminal palette.

flowchart TB
    A["OS appearance: Light or Dark"] --> B["WezTerm"]
    B --> C["Catppuccin Latte or Mocha color scheme"]
    B --> D["appearance file"]
    D --> E["zsh precmd hook"]
    E --> J["COLORFGBG"]
    J --> K["Claude Code light or dark theme"]
    C --> G["OpenCode TUI"]
    C --> F["Starship prompt symbols"]
    A --> H["Neovim system theme helper"]
    H --> I["Catppuccin Latte or Mocha"]

Neovim is the exception: it does not trust terminal colors and runs its own detection, which is covered in the Neovim config post. The others are new.

WezTerm
#

WezTerm exposes the desktop appearance through wezterm.gui.get_appearance(). It returns Light, Dark, LightHighContrast, or DarkHighContrast, and WezTerm reloads the config whenever the appearance changes. That means the config file only has to map the current value to a color scheme, and record it for the shell:

A few details are easy to miss.

wezterm.gui is only available in the GUI process. The mux server also evaluates the config, so calling wezterm.gui.get_appearance() without a guard fails there. The fallback keeps the mux usable; the GUI reloads the config and picks the right scheme anyway.

find("Dark") handles all four return values. Comparing with == "Dark" would silently turn high-contrast dark mode into the light scheme.

The appearance file sits next to the config, in wezterm.config_dir. The config only writes it from the GUI and only when the value changes, so the mux fallback cannot overwrite a real light with dark, and a reload does not rewrite the file for nothing. The path reaches the shell as WEZTERM_APPEARANCE_FILE. A WSL shell only inherits Windows variables listed in WSLENV, and the /p flag converts C:\Users\... to /mnt/c/Users/... on the way in. WezTerm’s own four variables are listed too, so they keep reaching WSL even if this setting replaces the value WezTerm would have built.

On Windows, default_domain makes every new window and tab a WSL shell. wezterm.default_wsl_domains() returns one WSL:<distro> domain per installed distro, and the config takes the first one. With several distros installed, name the one you want instead, for example config.default_domain = "WSL:Ubuntu". Other platforms skip the block.

PowerShell and cmd stay one key away. Ctrl+Shift+O opens a fuzzy launcher over launch_menu, whose entries name the local domain. Without that, an entry would spawn in the default domain and run inside WSL.

The built-in Ctrl+Shift+T spawns into the current pane’s domain, so a new tab opened from a PowerShell tab would start cmd. The config rebinds it to SpawnTab("DefaultDomain"), which always opens WSL.

Splits have the same problem in reverse. A split should stay in the pane’s domain, but the local domain’s default program is cmd, so splitting a PowerShell pane gave cmd. On Windows the split keys run a callback instead: in a local pane it checks the foreground process and splits with cmd for cmd and PowerShell for anything else, while WSL panes split as before. WezTerm binds each split to several key variants, so the config replaces all six; wezterm show-keys should list no SplitVertical or SplitHorizontal left.

The font is the CN build of Maple Mono NF, which carries the code, prompt, and Chinese glyphs in one family, so no fallback chain is needed.

The rest is tab handling. WezTerm closes a tab with Ctrl+Shift+W out of the box but has no binding to rename one, so Ctrl+Shift+E asks for a title and sets it with tab:set_title(). Submitting an empty title resets the tab to the running program’s name. With hide_tab_bar_if_only_one_tab, the title only shows once a second tab is open.

WezTerm has no built-in cheat sheet short of wezterm show-keys, which dumps every binding. dotfiles/wezterm/keys.txt is a hand-kept list of the common ones, installed next to wezterm.lua. Each [Group] header starts a section and each action = keys line is one binding:

1[Tabs]
2new tab = Ctrl+Shift+T
3close tab = Ctrl+Shift+W

A plain dump of such a list is tiring to read, because actions and keys look alike. The wezkeys function in ~/.zshrc lays it out two bindings per row, with the group in magenta, the action in the default color, and the key in bold blue. Those are ANSI colors, so they follow the Latte or Mocha palette. It runs when the first shell of a new tab, window, or split starts, and finds the file through the directory of WEZTERM_APPEARANCE_FILE, so the same lookup works on Linux and under WSL:

 1# WezTerm has no key cheat sheet of its own, so render the one installed next to
 2# wezterm.lua: two bindings per row, actions in the default color and keys in
 3# bold blue, so the eye can tell them apart without reading.
 4wezkeys() {
 5    local sheet="${WEZTERM_APPEARANCE_FILE:h}/keys.txt"
 6
 7    [[ -n $WEZTERM_APPEARANCE_FILE && -r $sheet ]] || return
 8    awk '
 9        BEGIN { group = "\033[1;35m"; key = "\033[1;34m"; off = "\033[0m" }
10        function end_row() { if (n % 2) printf "\n"; n = 0 }
11        /^#/ || /^[[:space:]]*$/ { next }
12        /^\[/ { end_row(); gsub(/\[|\]/, ""); label = $0; next }
13        {
14            split($0, part, / = /)
15            if (n % 2 == 0) { printf "%s%-8s%s", group, label, off; label = "" }
16            printf "%-18s%s%-22s%s", part[1], key, part[2], off
17            if (++n % 2 == 0) printf "\n"
18        }
19        END { end_row() }
20    ' "$sheet"
21}
22
23# Print it when the first shell of a tab, window, or split starts, with a dim
24# hint that `wezkeys` shows it again. Nested shells skip both.
25if [[ $TERM_PROGRAM == WezTerm && $SHLVL -eq 1 ]] && wezkeys; then
26    print -r -- $'        \e[2mrun `wezkeys` to show this again\e[0m'
27fi

The list is not generated from the config, so a new binding in config.keys needs a matching line in keys.txt. wezterm show-keys is the check: every key in the sheet should appear there with the expected action.

Starship
#

Starship stays on Mocha in both modes. An earlier version switched it to Latte with the desktop, through a precmd hook that pointed STARSHIP_CONFIG at a generated Latte copy. The palette values were Catppuccin’s own, but the result was hard to read in daylight. Latte’s accents are mid-tone colors designed as text on a light background, not as fills, so the filled bar had too little contrast with either light or dark text on top:

SegmentLatte fill, crust textLatte fill, text textMocha fill, crust text
red4.101.478.10
peach2.252.6810.59
yellow1.983.0514.76
green2.532.3912.61
sapphire2.372.549.93
lavender2.402.5110.48

Those are WCAG contrast ratios, where 4.5 is the usual floor for text. Mocha’s pastel fills under its near-black crust clear it by a wide margin, and they still stand out against a light terminal background, so one palette serves both modes and the switching hook is gone.

Text outside the bar is different: it sits on the terminal background, which does change. The prompt character and the command duration therefore use numbered ANSI colors such as fg:2, which WezTerm maps to Latte or Mocha with the rest of its palette. A named color like green would resolve to the Mocha palette and fade on a light background.

One setting in that file is not about color. Starship reads repository state with gitoxide by default, and gitoxide counts the files inside an uninitialized submodule as untracked. This repository keeps themes/blowfish as a submodule but has the theme files on disk without a .git entry, so git status was clean while the prompt showed a ?. Setting use_git_executable = true makes Starship ask git itself, which brings the prompt back in line with git status. It costs one git process per prompt, which is a fair trade for a status line that means what the command says.

The scan_timeout line at the top is there for WSL. Before drawing the language modules, Starship lists the current directory to look for files such as package.json or Cargo.toml, and gives up after 30 ms by default. A cold listing of a Windows drive under /mnt/c goes through WSL’s file share and can take longer, which prints a Scanning current directory timed out warning above the prompt. Allowing 200 ms keeps the scan quiet without slowing prompts in directories that answer quickly.

mode: "system" means OpenCode follows the terminal’s reported light or dark appearance. The theme itself still supplies its own Catppuccin colors, so this picks the matching half of the theme rather than sampling the terminal.

There is also a theme named system, which derives its colors from the terminal’s foreground, background, and ANSI palette. Setting both fields to system gives a TUI that copies WezTerm exactly, including any future palette change. Keeping catppuccin is the safer choice here: the terminal and the TUI then agree on the flavor even if one of them updates its built-in palette.

The TUI watches cli.json and applies valid edits without a restart.

Claude Code
#

Claude Code’s theme setting has an auto value, shown in /config as Auto (match terminal):

1{
2  "theme": "auto"
3}

With auto, Claude Code asks the terminal for its background color with an OSC 11 query when a session starts, and picks its light or dark theme from the answer. It asks again only when the terminal sends a color-scheme change notification (DEC mode 2031); there is no polling and no check on focus.

When nothing answers the query, Claude Code falls back to COLORFGBG, and without that to dark. Under WSL the query can go unanswered, so a light WezTerm still got dark diffs. COLORFGBG is an old convention of foreground;background color indexes, where a background of 0 to 6 or 8 means dark and anything else up to 15 means light. A precmd hook in ~/.zshrc derives it from the appearance file:

 1# Claude Code's auto theme asks the terminal for its background color and falls
 2# back to COLORFGBG when nothing answers, as can happen under WSL. Background
 3# 15 reads as light, 0 as dark.
 4terminal_colorfgbg() {
 5    [[ -r $WEZTERM_APPEARANCE_FILE ]] || return
 6
 7    if [[ $(<$WEZTERM_APPEARANCE_FILE) == light* ]]; then
 8        export COLORFGBG='0;15'
 9    else
10        export COLORFGBG='15;0'
11    fi
12}
13add-zsh-hook precmd terminal_colorfgbg

The variable only reaches programs started after the next prompt, so a running session keeps its theme after a desktop switch. Start a new session to pick up the other one. When the terminal does answer the query, that answer wins and the variable is ignored.

Neovim
#

Neovim already follows the system through lua/config/system_theme.lua. It does not read the terminal palette, because a terminal does not tell a full-screen application which colors it is using. Instead it checks the OS directly: gsettings on Linux, the registry on Windows and WSL, and defaults on macOS. That is why it belongs in the same story but not in the same mechanism.

Keeping the Neovim flavor pair aligned with WezTerm is enough:

1-- lua/plugins/colorscheme.lua
2background = {
3  light = "latte",
4  dark = "mocha",
5}
